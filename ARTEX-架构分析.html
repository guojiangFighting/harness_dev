02总体分层

关键工程选择是进程内单体的 goroutine 编排——没有外部队列、没有独立 agent 进程，每个任务就是「1 个 plannerLoop + N 个 workerLoop」两组 goroutine，状态全部落在 Postgres 双图里。这让「重启即恢复」非常简单（重启后任务从图状态续跑），代价是单机扩展上限。

03核心设计一：双图架构（系统的数据脊梁）

把「目标是什么」和「测到了什么程度」拆成两张图，靠锚点相连 db/schema.sql:153-283：

资产图（全局共享真值库）

  • companies / assets / company_scope
  • 六类节点：root_domain / ip / subdomain / app / service / endpoint
  • 每类用部分唯一索引做去重 key（endpoint=(url,method)，service 按 http/other 分两种）
  • 父子关系、归属、去重全部由程序计算，Agent 只提交原始信息（insert_assets）——机制上防止模型污染真值库

探索图（每任务独立推进链）

  • 七种节点 begin/goal/intent/fact/finding/hint/digest
  • 每种 kind 独立状态机 CHECK 约束（intent 八态：open/running/paused/done/blocked/exhausted/stopped/deleted）
  • 五种边：spawns / derived_from / yields / proves / covers
  • 每步执行写 activity 过程库
  • 意图即任务队列：frontier 是部分索引 WHERE kind='intent' AND state='open' ORDER BY priority DESC schema.sql:239，worker 用 claimNext（CAS 式 state 翻转）领取——双图同时就是调度数据结构。
  • 资产测试覆盖度：沿锚点表既能沿探索方向看「打的是哪些资产」，也能从资产反查「被哪些意图测过、得出过什么」；前端力导向覆盖图（范围内资产 + 已测高亮）就是这张表的视图。

→

③ 执行

→

④ 写回

fact / asset / finding 写回双图 → 触发下一轮规划；prove_goal 逐个证明目标后任务落 done

← 事件驱动闭环：图一变就唤醒 planner，直到目标全部被证明 →

防御性状态门（并发正确性）

  • paused / deleting / 终态 / 超时收尾中（settling）/ goalless（人工直投）各有独立分支 engine.go:880-938
  • beginTaskOperation 计数防止 delete 在「LLM 返回与最终 DB 写回之间」观察到假静止 engine.go:939
  • kill_work 用 context.WithCancelCause 按单条意图粒度取消，而非杀整个任务
  • goalless 分支：无 open 目标时 planner 不跑（跑了会误杀用户直投意图），任务结束改由 frontier 抽干决定——纯 Go 判断，不烧 LLM

05核心设计三：三个自主性机制

机制实现解决的问题
worker 间过程级信息交换 search_all_worker_traces / get_worker_trace agent/tools.go：在本任务其他 work 的 activity 过程库按关键字检索（自动排除自己）、按步骤取详情 有价值的观察（报错/隐藏参数）常出现在执行过程里而非正式 fact；信息以「执行过程」为粒度横向流动，边界不变
planner 共享 todolist TodoStore 按 explorationID 持久 agent/planner.go:110；planner 每次唤醒是全新会话，清单跨唤醒共享 多步串行利用链（发现注入点→取凭据→横向）记录一次，每轮只对「前置 fact 已存在」的下一步派意图——在无状态会话 + 事件驱动环境下稳定推进多步链路，是全系统最关键的一手
steer / kill 干预 steerHooks 在 worker 下一次工具调用前 drain 纠偏消息 engine.go:550；planner 与主 agent 均可注入 运行中的意图可被中途纠偏或按粒度终止，无需等整轮结束

06核心设计四：上下文生命周期（cold-digest）

长任务跑几十轮，探索图会膨胀。ARTEX 的做法不是 token 窗口截断，而是图上的冷节点压缩（agent/coldgraph.go + agent/compaction.go）：

  • coldgraph.go 刻意做成无 DB、无 LLM 依赖的纯图算法（冷判定、连通块分组 §3、同父单例拯救 §3.1），便于单测；
  • 节点带 content_version 与 cold_since_round：连续 ≥R 轮无下游分支即「冷」；压缩把 ≥2 的冷节点块经 LLM 折叠成 digest 节点（covers 边指回成员），状态机内置 active/superseded 支持版本更替；
  • 三种模式：maintain（每轮同步簿记，不调 LLM）、minor/major（后台折叠，签名不变的 body 复用 §5.3）；
  • 提交前活性复查：压缩期间复活的成员被丢弃，digest 永不覆盖热节点；每任务同时只一个压缩、冷却间隔。

07核心设计五：安全边界与审批体系

这是工程上最有特色的部分：把「平台治理」和「目标防御」刻意区分开。治理策略本身也是数据（DB 规则，可禁用可删除），不硬编码在引擎里。

  • Observer 失败归因（postToolUse，G5）：工具结果分类为 blocked/error/ok，planner 据此换策略而非在 403 上重复撞墙 guard.go:143-163。

  • 资产拦截规则 asset_intercept_rules / task_intercept_rules：网络层限制任务能访问什么。
  • MCP 服务端 server/mcp_server.go：对外暴露 list_tasks / spawn_task / pause / resume / add_task_hint；令牌分权限范围（read / task:create / task:control），支持企业限定、每小时建任务上限、来源白名单（可信代理 X-Forwarded-For 解析）、调用审计留 2 万条。README 坦率解释了「/mcp 为何不经过 Basic Auth」（一个请求只有一个 Authorization 头）。
  • 全量审计：每次工具调用过 PreToolUse 留环形 2000 条审计；拦截历史/任务拦截页/审批记录详情三处可查。

08支撑子系统

模块设计要点
traffic/（4.4k 行）基于 go-mitmproxy 的记录型 MITM 代理（:8788），CA 证书留痕；worker 所有 HTTP 强制走代理，请求/响应落 SQLite（大 body spill 到磁盘），漏洞可绑定流量证据回放；上游代理链、passthrough 域名、UA 随机化（20 个浏览器样本轮选，HTTP_USER_AGENT.md 逐出口排查）
llmpool/多 LLM 配置链式 failover：Rank 高者先行、同 Rank 轮流领队做负载分摊；健康策略 + 任务级绑定；绑定配置不可用时不回退默认模型而是暂停该 worker 槽位 engine.go:763
llmrec/LLM 调用录制（「LLM 记录」页审计与复现）
finding 工作流漏洞上报（addFinding）→ Reporter Agent 归并：同一实际缺陷折成 finding_case 文件夹 + 统一报告（候选分页检索、证据按需读、写入校验版本）→ retester Agent 复测（仍可复现/已修复/无法确认，成功即自动改状态）→ 统一导出
enrich/DNS/HTTP 异步补全（dnsx/miekg）：资产入库后台补 favicon/标题/技术栈，不占 worker 时间
notify/飞书/钉钉/企微/Telegram/Email/Webhook 六渠道 + 事件过滤 + 脱敏（notify/mask.go）
sidequestion/人在环路的侧问：独立小会话回答操作员对当前执行的问题，不污染主 agent 上下文
selfupdate/ + start.sh页面一键更新：SHA256 校验 → -h 冒烟 → 暂存 artex.new → 退出由守护脚本换装 → 连续 3 次启动失败自动回滚 artex.old
scheduler/ + agent_triggers定时/事件（finding、goal、工具调用）触发自定义 agent run，串行/并行与合并模式可配
任务归档 / ScopeSentry 同步归档 v4 格式（兼容读 v1–v3）；从 ScopeSentry 按项目/任务维度导入资产
mcphttp/ARTEX 作为 MCP 客户端调外部 MCP server（SSE + Streamable HTTP 双传输）——与「对外提供 MCP」是两个方向

09前端与 skills

前端：Next.js App Router 静态导出（web/src/app/）——(auth)/login|setup、(main)/dashboard | chat | function/{tasks, findings, assets, traffic, workspace, repeater, commands, schedules, llm-records, sync}、system/{agents, llm, tools, skills, mcp, intercept, notify, settings, logs}。亮点是资产覆盖图（力导向图 + 已测高亮 + 折叠展开）与探索链路可视化（直接渲染探索图血缘边）。NEXT_PUBLIC_MOCK=1 纯前端 Mock 模式支撑在线 Demo，i18n 中英双语。

skills/：SKILL.md 格式（同 Claude skills 生态），api-recon（明确声明「仅侦察、禁止漏洞利用」的边界表）、playwright-cli、scopesentry。技能是 markdown 提示 + 脚本包，经 skills 目录绑定给 agent。

工具目录：内置工具经 agent/toolcatalog.go 播种进 DB tools 表——handler 永远在代码层，DB 只能改模型看到的描述与缺省入参；按 agent 过滤绑定（mainagent/planner/worker/goals/auto/pentest/asset_mapper），Web 端「工具」页可管理。

10工程特点与评价

亮点

  • 双图 + 锚点：过程与事实各归其位；frontier 直接建在图状态上，调度与状态零冗余。
  • DB 约束做并发正确性：每种节点独立状态机 CHECK + CAS 式 claim，多 goroutine 不靠分布式锁也保持一致。
  • cold-digest：上下文压缩变成图操作，纯算法层可单测，签名复用 + 活性复查工程上很细。
  • 治理体系完整：平台管控 vs 目标防御的语义区分、三级审批流水线、审计全覆盖，远比同类 agent 产品细致。
  • 交付链成熟：schema 幂等迁移（重启即迁移，CHECK 变更都有 DO $$ 重建）、单二进制五平台 + SHA256SUMS + 多架构镜像、页面一键更新带自动回滚。

代价与约束

  • 单机垂直扩展：状态全在 Postgres、引擎在进程内，没有水平扩展的故事；README 依赖本地 SQLite/文件目录。
  • 包边界靠文件名：server/ 5.3 万行里 API、编排、治理高度耦合在一个包内。
  • 审查依赖模型：LLM fallback judge 意味着安全审查本身依赖模型判断（规则优先缓解但不消除误判面）。
  • 设计文档外置：中文注释大量 §2.3/§5.1 式内部编号引用，但设计文档不在仓库，外部读者只能靠注释反推。
