Part I · DeepSeek Harness 与「万物皆插件」

结论：DeepSeek Harness（dsh）是基于 Cordis 的微内核 agent 运行时。 内核几乎只有抽象服务 + 一个可替换的循环插件；其余产品能力一律以插件挂载。 设计准则是 everything is a plugin（一切皆插件）。

1.1 总体定位

层级内容
运行时底座vendored Cordis（loader / hmr / schemastery…）
产品内核packages/core/*：session / tools / agent / agent-loop / system-prompt
能力族llm / fs / shell / mcp / skill…：Definition → Provider → Consumer
组装层packages/bundle/* + profile：web / headless / sdk / acp…
应用入口apps/{cli,web,desktop}，统一经 dsh --profile 启动
扩展依赖接口（ctx.agents / ctx.tools / ctx.llm…），禁止依赖具体 loop 实现。 包括 dsh-agent-loop 在内也是插件。

1.2 Cordis 五要素

  1. Plugin：apply(ctx) 函数、带 apply 的对象、或 Service 子类
  2. Context：共享服务仓库，如 ctx.tools / ctx.llm / ctx.sessions
  3. inject：用服务依赖表达加载顺序（不是 YAML 行序）
  4. Typed Events：emit / waterfall / parallel / serial / bail
  5. 可逆 effect：注册带 disposer，卸载自动撤销

插件不互相 import 实现，只通过 ctx 与事件协作。

1.3 启动 = 叠一层插件树

空入口列表
  → profile 有序 bundles（如 dsh-base → dsh-web-app）
  → profile 的 cordis.patch.yml
  → Harness home patch
  → CLI --patch overlays
  • profile：具名组装（web / headless / sdk…）
  • bundle：Cordis 配置行 + 依赖代码的分发单元
  • patch：按 id 整行替换或 insert

dsh-base 的 cordis.patch.yml 把 LLM、session、agent、tools、agent-loop、 fs/shell/sandbox、插件管理器等全部写成可被上层覆盖的行——这就是「没有特权内核，一切可配置替换」的物理形态。

1.4 能力 Seam

一项可替换能力 = 三种角色（可同包，但概念上分离）：

Service Definition  →  Service Provider  →  Consumer（常是面向模型的 tool）
     dsh-shell             dsh-bash-local         dsh-tool-bash
     ctx.shell             本地执行               inject: ['shell','tools',…]

换 Provider（本地 → SSH/远程沙箱）时，Definition 与 tool 不变。 同类：ctx.llm 适配器、ctx.fs、ctx.sandbox、MCP、skill、subagent、web-search…

1.5 一轮对话控制流

turn/start
  → 领取输入 → 组装 prompt + tools
  → agent/pre-step（waterfall：接纳/改写/拒绝）
  → step/start → prepareCall → llm/stream
  → tool/call → tools/pre|execute|post → tool/result
  → 欠请求则下一 step
  → agent/turn-stopping → turn/end

原则：模型可见即已落日志；UI / 遥测 / fork / resume 都从 session log 派生。

1.6 一句话心智模型

配置树（YAML patches）
    ↓ Loader 挂载
插件森林（各自 inject + apply）
    ↓ 贡献
ctx.* 服务 + 类型化事件 + 可逆注册
    ↓ 其中一个插件
agent-loop 驱动 turn/step
    ↓ 其它插件
tools / llm / fs / policy / UI / MCP …

Part II · 自研 Runtime Harness，基座作承载

结论：长程任务的瓶颈往往不在「再换一个更强模型」， 而在你自己写的 runtime harness 如何管状态、验收与续跑； agent 基座只负责承载单轮 / 短程执行。

2.1 这句话在说什么

业界公式几乎统一成：

Agent ≈ 基座（认知 + 通用执行） + Harness（业务运行时）
层职责谁来做
Agent 基座（carrier） 模型调用、工具执行、session/turn、沙箱、基础 UI/SDK Claude Code / Codex / DeepSeek Harness / 自研微内核
Runtime harness（自研） 业务目标分解、跨窗口状态、验收门禁、续跑策略、领域工具与审批 你按业务写

「基座作承载」不是再造一个 Claude Code，而是： 把通用执行能力当可插拔引擎，把业务差异收敛到外层 / 旁路 harness。

2.2 为什么长程任务特别吃这一套

  • LongHorizon-Harness：同一骨干模型上，MEA 外环把 WeaveBench 从 51.8% 提到 80.7%；可挂 Claude Code / Codex 等现成基座作 executor。
  • Anthropic：长程失败主因是跨 context 失忆、一次做太多、提前宣布完成、脏现场。 靠 initializer + progress/feature 清单 + 每 session 只推进一点来修。
  • Harness 消融研究：planning / action space / context 管理各自作用不同； 弱模型更吃规划与工具约束，强模型更吃成本与上下文预算。

长程三难：目标漂移、context rot、任务状态丢失——几乎全是 runtime 问题，不是下一 token 问题。

2.3 业界常见实现形态（由薄到厚）

A. 薄外环 + 厚基座（最快落地）

基座不动；外层只加「续跑契约」。

  • Ralph：同一 prompt 反复喂；进度落在文件/git；Stop hook 或子 agent 轮次阻止提前退出。
  • Anthropic long-running：首 session 写 feature_list / progress / init.sh；之后每 session 读 git+进度、只做一个 feature、测完再标 passes、干净提交。

业务适配点：验收标准、进度 schema、允许改哪些文件、何时算 done。

B. MEA 外环 + 现成 agent 作 executor

Manager（持有任务状态，不碰环境）
  → 发子任务合同（目标/验收/边界）
Executor（Claude Code / Codex / dsh agent… 全新上下文执行）
  → 改环境
Auditor（只读验环境）
  → 认证事实写回任务状态

要点：执行轨迹可扔；只有审计过的任务状态跨轮持久化。 AgentAdapter 让基座可换，不改其原生 loop。 这正是「runtime 自研、基座作承载」的教科书结构。

C. 可组合基座上挂业务插件（DeepSeek 路线）

基座提供 ctx.agents / tools / sessions / llm…；业务 harness 以插件/bundle/profile 出现：

业务诉求挂接点
同会话长目标goal（phase、round 上限、blocked 原因）
跨轮全新 agenttool-ralph（不可变目标 + 有界报告 + 共享工作区）
领域编排workflow + subagent
定时续跑schedule
领域工具/审批/沙箱Definition–Provider–Consumer seam

循环仍是通用 agent-loop；业务差异不进内核，进配置树与插件。

D. 全自研 harness（成本最高）

从 observation / context / control / action / state / verification 六件套自己造。 适合强合规、强领域协议；多数团队应先 C/B，只把「不可换」的部分下沉。

2.4 分层总览图

Part III · 六件职责与落地选型

3.1 Runtime Harness 的六件职责

  1. Observation — 业务能看见什么（票据/DB/工单/浏览器，而不是裸 bash）
  2. Context — 每轮塞什么；旧轨迹如何压缩/丢弃
  3. Control — 谁决定下一子任务：单 loop / MEA / Ralph / goal-round
  4. Action — 工具面与权限（窄工具常比万能 bash 更稳）
  5. State — 任务状态放在上下文外：JSONL / goal / progress / 看板
  6. Verification — 独立验收：测试、审计 agent、业务规则引擎

3.2 长程适配业务的关键操作

  1. 状态外置：不要让模型在同一上下文里既干活又当裁判。
  2. 短执行、长记忆：executor 可 fresh；记忆是审计过的状态 + 工件。
  3. 合同化子任务：每轮有验收标准；未审计「完成」不得写入正式状态。
  4. 基座可替换：业务环只依赖 Adapter（run(subtask) → artifacts）。
  5. 完成条件可机器判定：测试、字段校验、页面断言；忌纯「模型自评 done」。
  6. 干净交接：每轮结束留下下一位 agent 能快速读懂的 progress + 可恢复 git/工件。

3.3 映射到 DeepSeek Harness

agent 基座（Cordis + core + agent-loop）
        ↑ 承载
业务 runtime harness = profile/bundle/patch
  + 领域 tools/providers
  + goal / ralph / workflow / schedule
  + 业务验收与审批插件

3.4 实践选型

场景建议
明确验收、可迭代改代码/文件 薄外环：Ralph / Anthropic progress 模式
跨系统、易撒谎完成、需强证据 MEA：Manager + fresh Executor + 只读 Auditor
要产品化、多入口（Web/SDK/定时） 可组合基座（如 DSH）+ 业务 bundle
强合规、工具协议极定制 自研六件套，基座只留模型与最小执行
反模式：把业务状态全塞进一份越聊越长的 transcript； 让执行 agent 自己标 done；为每个业务 fork 一整份 agent 产品而不是挂 harness。
一句话：自研的是「如何把长任务拆成可审计状态转移」的 runtime； 基座只是可替换的执行载体。 长程适配业务 = 外置状态 + 短上下文执行 + 独立验收 + 干净续跑，而不是改模型权重。

Part IV · LongHorizon 与 DeepSeek 插件栈

结论：两条路不在同一层。LongHorizon 是任务状态外环；DeepSeek 插件 / bundle / profile 是可替换的 agent 产品基座。长程业务通常两边的职责都要，但不必两边都从零写。

4.1 理解校准

可以把它看成凌驾在 agent harness 之上、靠调用 agent 推进任务的外环。固定的是三种角色，不是一群长期存活、各自保存完成状态的专职 agent。

  • 它不改 Claude Code / Codex / dsh 的原生 loop，经 AgentAdapter 调用它们。
  • Manager 持有任务状态且不碰环境；Executor 每轮全新上下文，轨迹用完即弃；Auditor 只读检查环境。
  • 持久化的是任务状态：需求、产物、事实，以及 completed / pending / blocked / untrusted。完成只能由 Auditor 对环境的核查写入。执行 agent 自己说做完了不算。
  • 调用 agent 只是 Execute 这一步。长程能力来自把「谁在干活」和「什么算做完」拆开。
Manager（持有任务状态，不碰环境）
  → 子任务合同
Executor（全新上下文，唯一可改环境）
  → 环境变化
Auditor（只读核查同一环境）
  → 审计事实写回任务状态
  → 下一轮 Manager

4.2 LongHorizon-Harness 的优势

  • 长程三难被结构拆开：目标漂移靠合同与原目标对照，context rot 靠丢弃执行轨迹，状态丢失靠外置任务记录。
  • 基座可换。业务环只依赖 run(contract) → report，不绑死一家 CLI。
  • 控制权在部署方脚本，不在模型。模型不能改循环、路由或验收规则。
  • 论文侧有跨基准增益（同一骨干下 WeaveBench 51.8% 到 80.7% 等），说明外环本身有独立价值。
  • 适合跨系统、容易谎报完成、必须用环境证据的任务。

4.3 LongHorizon-Harness 的劣势

  • 它是研究型外环，不是产品基座。会话产品、凭据、审批、沙箱、Web/SDK、插件市场都要自己接，或继续依赖所挂的 CLI。
  • 质量瓶颈在 Auditor。环境不可观测、验收含糊、只读工具不够时，外环会把错误状态写死。
  • Manager 看不到现场，合同写错会让 Executor 空转；每轮全新上下文更费 token，短任务不划算。
  • Adapter 要跟着 Claude Code / Codex 的 CLI 与权限模型变。
  • 浏览器、定时、人在环审批不是它的交付形态，需要再包一层。

4.4 DeepSeek 插件 / bundle / profile 的优势

基座已有 append-only session、工具流水线、agent/pre-step、沙箱与审批，以及 Web / headless / sdk / acp。业务差异用叠层表达，不必 fork 循环。

  • 插件：领域工具、策略、验收服务，走 inject 与可逆注册。能力按 Definition / Provider / Consumer 拆开。
  • bundle：可分发的 cordis.patch.yml，插入一组行，上层按 id 整行替换。
  • profile：web / sdk 等具名组装。树外包用 dsh plugin --profile <name> add 装入，不必改发行版内核。
  • 相邻件已经存在：同会话长目标用 goal；全新子 agent 与有界交接用 tool-ralph；编排用 workflow；定时用 schedule。
  • 同一业务层可以同时出现在 Web、SDK、headless。人在环、权限、日志回放、取消沿用基座。

4.5 DeepSeek 路线的劣势

  • 默认是一条会增长的 session。goal 留在同会话，压缩不能替代外置任务状态。
  • ralph 不做独立审计。它是新鲜执行加有界交接，不是 MEA。
  • 长程环若只做成普通工具，模型可以不调用它。控制权要放在部署方固定脚本或启动器外环。
  • 插件开发成本高：包拓扑、schema、README、locale、覆盖率门禁。预览期 API 会破坏兼容。
  • 插件挂在 dsh 的 ctx 上。换掉整个执行基座，就用不上这套插件收益。

4.6 能否接入任何 agent

不能接任意 agent。能接的是满足 AgentAdapter 契约的执行后端。论文中的例子是 Claude Code、Codex CLI、OpenClaw、Hermes。三种角色可以换模型和 harness，原生 loop 保持不动。
  • 能在有界预算内跑完一份子任务合同，并返回结构化执行报告。
  • Executor 使用全新上下文，不继承父会话，并能按合同改环境。
  • Auditor 只能只读检查同一环境。
  • Manager 不直接拿环境工具，只产出 execute / done / blocked / ask 和下一份合同。
  • 能取消、能限制轮次，交接内容有大小上限。
纯聊天、无法隔离上下文、或不能把「完成」交给外部检查的 agent，接上也不会变成长程系统。

4.7 DeepSeek 给 LongHorizon 的加成

加成发生在每一轮 Execute / Audit 里面，不替代外环的任务状态。对应长程复杂业务：

  • 业务动作面。用 profile 挂上 ERP/MCP、文件系统、浏览器、Office，而不是把一轮合同丢给裸 bash。Auditor 走同一套只读能力查现场。
  • 权限与沙箱。付款、生产写、越权命令由审批和 sandbox 挡在工具执行前。外环的 ask 只决定要不要问人，挡不住这一轮内部的危险调用。
  • 可核对现场。session 日志、带 schema 的工具结果、附件和工作区文件，给 Auditor 当环境证据。完成仍以环境为准。
  • 干净的新上下文。子 agent 可以要求 inheritsParentContext: false，父对话不会漏进下一轮。
  • 多入口承载。headless/sdk 进程充当被调用的 Executor；定时调度唤醒下一轮 Manager。
  • 执行世界可换。文件系统和子进程指向同一远程沙箱时，命令行、终端和语言服务一起搬走，合同不用按机器重写。
goal 和 ralph 不能算这层加成。它们没有独立的环境审计，放进 LongHorizon 里会和任务状态抢「谁说了算」。

4.8 怎么选

场景建议
把现有编码 CLI 变成可审计的长任务状态机，短期不需要自有产品壳 用 LongHorizon 式外环，dsh 或 Claude Code 只当 Executor
做成自己的多入口 agent 产品，长程只是其中一种工作模式 用 dsh 的 profile/bundle，把业务工具和策略做成插件
两者都要 dsh 当 Executor 与产品壳；外环照抄 MEA。现成 goal / ralph 不等于 LongHorizon

Part V · ARTEX 与 LongHorizon 对照

结论：思路同属「外环拆角色、状态放在执行轨迹外面」，但不是同一套设计。 ARTEX 没有 LongHorizon 那种独立只读审计；它的创新在渗透测试场景里的双图、并发前沿队列，以及「没写回图就不算做完」。
依据公开源码注释与包文档（agent 包、tools.go、Planner / Worker / MainAgent 说明）。 仓库根 README 曾拉取失败，架构长文 docs/ARTEX-架构设计.md 未逐段核对。项目： github.com/BaaRai/ARTEX。

5.1 一致的部分

两边都拒绝「一个 agent 一路聊到任务结束」：

共同想法LongHorizonARTEX
规划与执行分开 Manager 发合同，Executor 只做这一份 Planner 是唯一意图生成者，Worker 只领一条 intent
一次只做一块 一轮一个有界子任务 一个 Worker 只 claim 一条 frontier intent，做完就退出
跨轮记忆不靠聊天记录 任务状态 + 审计报告 PostgreSQL 里的资产图 + 探索图
说完了不等于做完 执行报告不能直接标完成 WriteCounts.Total()==0 表示探过但没落库，不当成完成；结束原因区分 completed 与 max_turns

人也不在自主循环里。LongHorizon 的 Manager 可以 ask。 ARTEX 的 MainAgent 只观察、注入 hint 或高优先级 intent，自主发牌仍是 Planner 的事。

5.2 不一致的部分

LongHorizon 的关键是 Manage → Execute → Audit： Auditor 只读检查环境，只有审计事实能改任务状态，执行者的自述不能标完成。 每一轮执行上下文用完即弃，下一轮只看见压缩后的已验证状态。

ARTEX 的闭环是 Planner → 并发 Worker → 工人自己把 fact / asset / finding 写回图 → 图变化再叫醒 Planner。 Planner 读这张图判断目标是否达成。没有一个不能改环境、也不能采信工人报告的独立审计角色。 工人调用 report_finding 就会把发现写进探索图，并可以中途唤醒 Planner。 

LongHorizon:
  Manager → Executor（改环境）→ Auditor（只读）→ 任务状态

ARTEX:
  Planner → 并发 Workers（改环境并写图）→ 双图状态 → 再叫醒 Planner
  MainAgent 只注入 hint / 高优先级 intent，不替代 Planner
  • 顺序一轮 vs 并发前沿。LongHorizon 一轮一个 Executor。ARTEX 多个 Worker 同时领不同 intent。
  • 通用外环 vs 渗透专用运行时。LongHorizon 用 Adapter 套 Claude Code、Codex 等。ARTEX 自己接 LLM，工具是 Kali、流量录制代理、域名解析和站点探测。
  • 紧凑任务状态 vs 不断长大的双图。LongHorizon 丢掉执行轨迹。ARTEX 保留 transcript，并用 Compactor 压缩；权威记忆是图，不是一份短的审计记录。
角色拆分和「状态外置」一致；「完成必须由独立环境审计写入」这一条不一致。 ARTEX 更接近「规划器 + 工人写共享世界模型」，工人既是执行者，也是事实的写入者。

5.3 相对 LongHorizon 的新意

这些是针对渗透测试长程探索的设计，不是把 MEA 换了个名字：

  1. 双图世界模型。 资产图回答「目标上有什么」；探索图回答「试过什么、从哪来、产出了什么」。 intent 带 parents 和 yields，Planner 看到的是谱系，不只是一条状态摘要。
  2. 前沿队列。 开放 intent 按优先级领取，多个 Worker 并行。图一变就触发下一轮规划，不必等整轮审计结束。
  3. 停滞指纹。 把 intent 摘要归一化后，同一方向重复多次且自第一次尝试以来没有新 finding，就判定在空转。 用来截断「同一形状的攻击反复磨」。
  4. 结算门。 Worker 退出前进入强制结算，并关掉破坏性工具。墙钟超时、取消、写回计数分开处理。 探索过但 Facts + Assets + Findings == 0 不能当成进展。
  5. 环境侧富化。 流量走录制代理；发现域名或站点后触发解析和探测，把环境观察写进资产图。 这比纯模型自述更靠近现场，但写回仍由 Worker 路径发起，不是独立 Auditor。
  6. 人的干预面很窄。 MainAgent 可以读图、给 Planner 提示、或直接塞一条高优先级 intent，也可以中途 steer / kill 某个 Worker。 人改的是队列，不是替换 Planner。

5.4 怎么用这个判断

业务诉求判断
执行者不能给自己盖章 ARTEX 还没做到；要另加只读审计，并禁止 report_finding 直接改完成状态
未知攻击面、多线索并行、试错方向会重复 ARTEX 的双图、前沿队列和停滞检测比 LongHorizon 的单线合同更贴切
需要强验收可信 LongHorizon 的独立 Auditor 更合适
需要探索调度与领域世界模型 ARTEX 更强；可把其双图 / 前沿思路接到 MEA 外环，而不是互相替换

Part VI · 国内外调研与设计补强

结论：当前「MEA 外环 + DeepSeek 基座 + ARTEX 探索调度」方向成立。 Web 调研显示，行业共识已从「让模型多干一会儿」转向「外置状态、独立验收、可回放证据」。 可补强点主要是：任务状态与产物分离、提交门、多层验证、项目工作简报、权威系统读回，以及把业务策略写成可编辑 harness 文档。

6.1 国际：围绕 LongHorizon 的知识簇

来源核心思想对当前设计的含义
LongHorizon-Harness / MEA 任务状态外置；仅审计事实可写状态；Executor 全新上下文后丢弃轨迹；角色是循环内职责边界，不是三套独立记忆 已采纳。官方补充：被拒结果仍是证据不是进展；done 需 Manager 判定且审计干净
StateHarness 维护演化中的项目状态：问题/假设、发现与决策、仓库关系、未完成项；另开诊断会话复盘遗漏 任务状态之外再加「项目工作简报」。编码类长程可降低成本；与 MEA 互补而非替代
VeriHarness 把验证做成 agentic：工作区 + 证据工具 + 可复用验证技能；分歧消解器 vs 共识挑战者 Auditor 不应只做 checklist。要能反驳「大家都说对了」和「两套说法打架」

NLAH + IHR 把角色、阶段、状态规则、验证与停机条件写成可编辑自然语言 harness 文档，由薄 runtime 解释执行 业务差异尽量进策略文档，不要硬编码进 Manager 脚本
Meta-Harness 用编码 agent 根据分数与原始执行轨迹搜索/改写 harness 代码 外环本身可迭代优化；保存完整轨迹与评分，供后续改合同/审计策略

6.2 国内：协作治理与 DSH 生态

  • 阿里云 AI Agent Handbook： 协作应拆成 Task State（目标、责任、依赖、进度、验收）与 Artifact（报告、代码、数据、测试结果）。 成员退出后仍能靠状态与产物续跑，减少自然语言转述损失。
  • 生产级多智能体系统： 多 Agent 首先是控制权、责任、状态和故障边界的设计。 会话视图只是投影；策略决策与审批应是独立状态机；关键事实用仅追加事件账本，Agent 不可改写。
  • ToWow Agent-to-Agent Harness： 协议负责连接，Harness 负责治理。最小证据循环： 定义任务 → Context Capsule → 执行留痕 → Commit Gate → 权威系统读回 Effect → 独立验收。 「工具自报成功」不等于「目标端已生效」。
  • DeepSeek / 36氪解读： DSH 把小事直做、大事 Goal、委派 Subagent、并行 Workflow、Ralph 失忆迭代分成不同模式。 社区插件 long-horizon-runtime 强调计划确认、进度跟踪与中断恢复——补的是产品壳，仍不等于独立环境审计。
  • ARTEX（国内渗透实践）： 双图 + 前沿并发 + 停滞指纹，强在探索调度；缺独立 Auditor，工人可写 finding。见 Part V。

6.3 行业共识（可写成不变量）

  1. 消息不等于状态；聊天记录不是权威任务状态。
  2. 执行自报不等于完成；完成只能来自环境或权威系统读回。
  3. 局部绿灯不等于整体交付；需要 Commit Gate / 独立评审。
  4. 跨轮只应传递压缩后的可靠信息（合同 / Capsule / 审计报告），不是整段 transcript。
  5. Harness 约束承诺与证据边界，不约束推理路径；探索可以自由，交付必须过门。
  6. 角色是职责边界，不是多套互相漂移的长期记忆。

6.4 对当前设计的具体补强

对照已有 Part I–V（MEA 外环、DSH 基座、ARTEX 对照），建议补强如下：

A. 状态模型升级

  • 把单一「任务状态」拆成：Task State（需求/进度/阻塞）+ Artifacts（可引用产物）+ 可选 Working Brief（项目假设、仓库关系、未完成债，来自 StateHarness）。
  • 记录状态四值保持：completed / pending / blocked / untrusted；被拒审计进入 evidence，不进 completed。
  • 需求清单仿 Anthropic：初始化后不可删改描述，只能翻转验收位。

B. 验证栈分层（补强 Auditor）

L0 合同内初始指令与验收标准
L1 执行中途提醒 / 预算与停滞检测（可借 ARTEX 指纹）
L2 Commit Gate：所有权、测试、影响范围、回滚点
L3 独立 Auditor：只读环境 + 权威系统 Effect 读回
可选 L3+ VeriHarness：分歧消解 + 共识挑战 + 验证技能库

MEA 的 Audit 对应 L3；不要指望一轮 Auditor 覆盖全部验证负担。

C. 交接与写入门

  • Executor 入场只带 Context Capsule：目标、边界、依赖、完成标准、相关审计引用。
  • 写回共享状态前过 Commit Gate；未过门的探索结果不得进入 Task State。
  • 业务系统（ERP/工单/DB）以 Effect 读回为准，不以工具返回值或模型自述为准。

D. 与 DeepSeek / ARTEX 的组合方式

  • DSH 继续提供动作面、沙箱、审批、session 证据、多入口与 fresh child。
  • 外环仍用 MEA；不要用 goal / ralph / 社区 long-horizon-runtime 替代独立审计。
  • 探索型业务可吸收 ARTEX：双图或前沿队列作 调度层，但仍要 L3 Auditor 才能标完成。
  • 业务策略可用 NLAH 风格文档描述角色/停机/验收，由固定 runtime 解释；机制层留在 Cordis 插件与 Adapter。

E. 可观测与可进化

  • 追加式 EventLog：谁、在什么 Capsule 下、做了什么、产物是什么、验收结论是什么。
  • 失败归因、干预记录、熵/失控审计进入产品指标，而不只看成功率。
  • 保留完整轨迹与评分，供 Meta-Harness 式外环优化（合同模板、审计技能、停滞阈值）。

6.5 建议的增强版闭环

Initializer
  → 不可变需求清单 + 空 Task State + 工作简报骨架
Manage
  → 选下一子目标，生成 Context Capsule / 合同
Execute（DSH / Claude Code / …，可并发于探索业务）
  → 改环境；关键动作进 EventLog
Commit Gate
  → 未通过则留在证据区，不写正式状态
Audit / Effect 读回（独立、只读）
  → 更新 Task State + Artifacts + Working Brief
停滞 / 分歧 / 共识挑战
  → 触发重规划或诊断会话
done | blocked | ask | execute 下一轮
补强后的系统仍是「runtime harness 自研、agent 基座承载」。 变化是：外环从「三角色 MEA」扩成「状态三分 + 多层验证 + 提交门 + 权威读回」； 基座仍负责执行与环境能力，不负责宣布完成。
