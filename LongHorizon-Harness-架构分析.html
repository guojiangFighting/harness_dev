01一句话定位

LongHorizon-Harness 不实现自己的 LLM Agent。它在现有 Agent CLI（Claude Code、Codex CLI、OpenCode、DeepSeek Harness）外面套一个「规划 → 执行 → 验证 → 保存/恢复」的执行闭环，让同一个 Agent 能跨桌面 GUI 和终端持续工作数十小时。核心理念是作者所称的 Loop Engineering：工程化模型外部的验证、纠错与恢复，而不是优化单轮 prompt。

03执行内核：三角色循环

主循环在 manager.py:168 的 _run_impl。每一轮（ManagedRound，types.py:92）按固定状态机推进：

① Manager 规划

读取「原始任务 + 自己维护的任务状态 + Auditor 报告」，输出计划；解析出 next_step ∈ {gui, cli, done, blocked, invalid, ask}

→

② Executor 执行

按 next_step 绑定 GUI 或 CLI Executor，全新上下文只做一个边界明确的子任务

→

③ Auditor 验收

独立检查真实文件/界面/日志，输出结构化 AuditReport；格式不合格先走一次格式修复 episode

→

④ 人工门禁

每轮结束评估触发条件（完成 / 轮次耗尽 / 阻塞 / 连续失败），必要时阻塞等待操作员决议

← 未完成则回到 ①，从原始目标 + 最后一个已验证检查点恢复继续；完成则输出最终报告 →

关键设计约束

  • 可信状态与不可信输出严格分离：Auditor 报告才是「可信中间状态」，Executor 的自述只是证据。Manager 宣称 done 时必须有此前一轮 clean 状态的 Auditor 报告背书，否则被驳回并注入修复信号 manager.py:525-563
  • 一切落盘，文件即状态：每轮写 logs/role_orchestration/rounds/round_XXX/（三角色的输入输出、任务状态、契约）+ 追加式 events.jsonl 事件账本，无数据库
  • 恢复 = 重建上下文：resume 从账本重放全部轮次、重建 Manager 规划上下文继续跑 manager.py:269-283，不做 checkpoint 序列化
  • 故障分级：角色超时是「可恢复失败」（记入账本，下一轮恢复）；provider 硬故障才终止（provider_errors.py）；任何崩溃都在 manager.py:128 的 run() 边界兜底写出终态报告，杜绝「进程死了但 supervisor 认为它还活着」
  • 角色独立预算：三角色各有 EpisodeBudget 超时（types.py:108），且每个角色可分别指定不同的后端与模型（Manager/Auditor 用强模型、Executor 用便宜模型）
  • 协议化角色输出：角色 prompt + 解析器（role_prompts.py:529 的 parse_role_manager_next_step 等）+ 格式修复 Agent，三层保证机器可读

04适配层：把 Agent CLI 变成一条 shell 命令

adapters/cli_agent.py:31 的 CommandAgentAdapter 是通用实现：prompt 写入运行私有的临时文件 → 按命令模板拼出 shell 命令 → env.exec 执行 → 用后端专属解析器从 stdout 提取可见输出 → 封装 EpisodeResult。各后端因此只是「命令模板 + 输出解析器 + 配置映射」的差异：

后端命令形态要点
CodexAdaptercodex exec --json ... < prompt.mdbase_url / 模型 / MCP 全部经 -c key=value 内联 TOML 覆盖，不改用户 ~/.codex；默认绕过自身沙箱 adapters/codex.py:25
ClaudeCodeAdapterclaude -p ...claude_permissions.py 按角色下发权限：Manager/Auditor 只读、Executor 可写工作区
OpenCodeAdapteropencode run prompt标准化 JSON 结果 + 按角色读写权限
DeepSeekHarnessAdapterdsh --profile headless隔离 DSH_HOME；headless 仅返回最终答案
  • 新增一个 Agent 后端 = 写一个几十行的适配器类，不动内核。
  • 适配器注入 hidden_paths 声明 cli_agent.py:122：明确告知 Agent 本 run 自己的日志目录是禁区，防止角色间上下文泄漏。
  • secret 脱敏内建在日志与可见输出路径上（cli_agent.py:24 的 redact_secrets）。

05进程模型与监督层

三种运行拓扑共用同一个执行内核：

拓扑入口结构
纯 CLIlh-harness run单进程跑循环
CLI + 内嵌面板lh-harness run --dashboard同进程起 FastAPI + attached_only 受限 supervisor cli.py:1737，可安全 stop/abort 自己
Web 工作台lh-harness webAPI 进程 + RunSupervisor，每个任务一个独立 worker 子进程

Web 拓扑下 create_run 通过 [sys.executable, -m, lh_harness, run, ..., --supervised] 拉起 worker supervisor/service.py:1391 —— worker 就是普通的 lh-harness run，supervisor 刻意不重写循环，只做进程归属与命令边界。API 进程与 worker 之间没有 socket，通信全靠 run 目录下的文件型 ControlBus supervisor/control_bus.py:464：

# runs/<run-id>/control/
commands.jsonl          # 追加命令（append-only）
command_receipts.jsonl  # worker 回执（applied/rejected/failed/cancelled）
status.json             # 生命周期状态（creating/running/waiting_approval/…）
owner.json              # pid 归属 + resume epoch
.control.lock           # flock 锁文件（序列化点，而非数据文件）

双端以 flock + 乐观 revision 并发控制。这一层的工程防御密度非常高（README 中「原生 Windows 不可用」的原因也在这里——依赖 POSIX 原语）：

  • symlink 防护：全程 O_NOFOLLOW 锚定打开，拒绝符号链接劫持 run 目录 control_bus.py:54-176
  • 幂等创建：Idempotency-Key + 请求指纹 + 先落盘 reservation 再 spawn；HTTP 重试 / 崩溃后重试都不会拉起第二个 worker service.py:1442-1558
  • resume epoch：以代数计数隔离旧 epoch 的命令回执 lifecycle.py:48
  • worker 认领校验：--supervised 模式认领 reservation 时逐字段校验（task/agent/model/pid 不匹配即拒绝）cli.py:233-345

人工门禁（human-in-the-loop）

dashboard/gate.py:106 的 make_human_hook：每轮结束由可插拔规则 dashboard/rules.py（默认连续 3 轮失败触发，阈值可用 LH_HARNESS_DASHBOARD_FAILURE_LIMIT 调整）分类出五种对话框：completed / max_rounds / needs_input / needs_human / repeated_failure，创建 approval 后阻塞等待 UI 决议；决议动作 + 附加指令 + 追加轮数注入下一轮。

DashboardState dashboard/state.py:155 是关键复用点——它既是 runs 目录的只读投影（rounds / artifacts / trajectory / 事件），又是 approvals 与操作员指令的持久化层，因此 worker 无 HTTP 服务也能参与审批流（control_enabled 模式，cli.py:1715-1724），同一个 human hook 在三种拓扑下复用。

07扩展面

MCP server

mcp_server/stdio_server.py:170 把 run 生命周期（lh_start_run / lh_run_status / lh_stop_run / 注入指令 等）暴露为 MCP 工具，内部复用同一个 RunSupervisor + ControlBus——所以别的 Agent（比如 Claude Code 本身）可以编程方式启动并监控 harness 任务，审批与指令走的也是同一条命令通道（inject_instruction 命令与 Dashboard 同路径）。

插件系统

plugins/：机器级安装 computer-use 插件（npm 分发），按 Agent 生成其原生格式的 MCP 配置文件（Claude 用 .mcp.json，Codex 用 TOML），运行时按 codex-computer-use > open-computer-use > clawdcursor 优先级自动选取 plugins/state.py:25。安装与任务执行彻底解耦：run 从不安装/修改插件，GUI 能力完全外包给插件。

10架构评价

亮点

  • 零侵入适配：不重写 Agent 循环，只用 run_episode 单接口包住任意 CLI，模型 / 后端 / 角色 三维自由组合。
  • 状态即文件：账本 + 事件流天然可检查、可恢复、可审计；resume 是重建上下文而非反序列化。
  • 验证是硬约束：把「验证」做成独立角色与机制约束（completion 必须有 clean audit 背书），这是其声称提升完成率的机制基础。
  • 工程防御密度高：幂等、symlink 防护、脱敏、有界读取、崩溃兜底——对长时无人值守运行是必要的。
  • 关注点分层的复用设计：core TS 逻辑与 React 解耦、human hook 三拓扑复用、supervisor 与 MCP/插件同一条命令通道。

代价与约束

  • 巨型状态机：核心循环 manager.py 近 2500 行，if next_step == … 分支重复模式多，扩展路由类型改动面大。
  • 文件 ControlBus 的边界：多机 / 远程场景不如消息队列，且依赖 POSIX 原语（Windows 需 WSL2，issue #70 跟踪原生支持）。
  • 环境抽象尚薄：Environment 主包目前只有 local 实现，GUI 能力完全外包给插件。
  • 评测副本漂移：eval 内嵌三份旧 harness（orchestrator/verifier）与主包（manager/auditor）概念命名不一致，维护上是已知债务。
